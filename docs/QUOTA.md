# We Match 交互额度体系

- 版本：v1.0（设计稿）
- 日期：2026-08-07
- 状态：待确认

## 1. 为什么要有额度

We Match 免费，且注册只要一个手机号。这两件事凑在一起，等于把发布和举手的边际成本压到接近零——对正常用户是好事，对刷子也是。

匹配类产品被玩坏只有两种方式：**广场被灌满没人看的需求**，和**用户被没人想理的举手淹没**。前者毁列表，后者毁体验，而且后者更致命——一个人收到 20 条群发举手之后就不会再回来了。

所以额度的目标不是省钱，是保住信噪比。定额原则只有一条：

> **95% 的正常用户永远碰不到上限，刷子第一个小时就撞墙。**

任何一个数值如果让老实用户感到别扭，就是定错了；如果刷子跑了一整天还没撞到，也是定错了。

额度不是收费墙。这里不设"充值扩容"，超出上限的唯一办法是把手上的事做完——这条要写死，一旦开了付费扩容的口子，整套设计的正当性就没了。

## 2. 四层结构

单一维度的限制永远能被绕开：只限每天条数，刷子就每天顶格发；只限速度，刷子就慢慢刷。四层各管一件事，缺一层就漏一类滥用。

| 层 | 管什么 | 时间尺度 | 正常用户感知 |
|---|---|---|---|
| L1 节流 | 机器连点 | 秒 | 无 |
| L2 日额度 | 单日灌水 | 自然日 | 极少 |
| L3 存量额度 | 长期囤积 | 无期限 | 偶尔 |
| L4 定向频次 | 盯人骚扰 | 天 / 周 | 无 |

L3 是这套设计里最重要的一层，也是现在完全缺失的一层。日额度只管流入速度：一天 10 条，一个月就是 300 条挂在广场上，日额度对此毫无办法。存量额度管的是"同时占着多少",这才是决定广场好不好用的量。

## 3. L1 节流

统一走现有的 `consumeRateLimit`（`lib/rate-limit.ts`，SQLite 固定窗口，重启和多进程都不清零）。这层纯粹拦脚本，正常人手速够不到。

| 动作 | 限制 |
|---|---|
| 发布需求 | 1 次 / 30 秒 |
| 发起举手 | 1 次 / 20 秒 |
| 提交举报 | 1 次 / 60 秒 |
| 组织加入申请 | 1 次 / 60 秒 |
| 编辑需求 / 名片 | 1 次 / 5 秒 |
| 任意写操作（按用户兜底） | 30 次 / 分钟 |

撞到 L1 一律回同一句「操作太快，请稍后再试」，不透露具体窗口——说清楚了等于告诉脚本该 sleep 多久。

## 4. L2 日额度

自然日 00:00（服务器本地时区）重置，与现有发布额度的算法一致。

**分两档。** 新账号降档是这一层的关键：注册成本低，刷子必然批量开号，让新号第一天只能发 3 条，等于把刷子的开号成本抬高三倍以上。

| 动作 | 新账号 | 常规账号 |
|---|---|---|
| 发布需求 | 3 | 10 |
| 发起举手 | 5 | 20 |
| 提交举报 | 3 | 10 |
| 组织加入申请 | 2 | 5 |
| 创建组织 | 1 | 2 |
| 需求续期 | 5 | 20 |
| 拉黑 | 20 | 50 |
| 编辑名片 | 30 | 50 |

**升为常规账号需同时满足：**

1. 注册满 72 小时；
2. 名片填了一句话介绍、至少 1 个标签、至少 1 项对外可见的联系方式。

第 2 条是顺手做的一件好事：想要完整额度，先把名片填好。这既提高了刷子的成本（要填够信息才能大量发言），又让广场上活跃的人都是能被联系到的人。UI 上要把它写成正向引导而不是惩罚——「填好名片，每日发布额度从 3 提到 10」，配一个直达「编辑名片」的链接。

## 5. L3 存量额度

不看时间窗口，只看此刻手上占着多少。用完不会自动恢复，只能靠把事情做完来释放。

| 存量 | 上限 | 释放方式 |
|---|---|---|
| 同时开放的需求（open 且未过期） | 20 | 标记完成 / 关闭 / 自然到期 |
| **等待回应的举手（pending）** | **5** | 被接受 / 被拒 / 自行撤回 / 需求关闭 |
| 已连接未完成（accepted） | 10 | 双方确认完成 / 撤回 |
| 待审批的组织申请 | 3 | 管理员处理 |

### 「等待回应的举手 ≤ 5」是整套体系的核心阀门

这一条比日额度重要得多。它精准区分了两类人，而且不需要任何判别逻辑：

- 认真找人的人，同时盯着 2 到 3 个机会，一辈子碰不到这个上限；
- 群发的人，第 6 个就卡住，而且必须等别人回应才能继续——**他的速度被他打扰的人的耐心接管了**。

日额度 20 依然在，但实际能不能用满，取决于前面的举手有没有回音。这是一个自我调节的机制：举手质量高的人流转快，额度形同虚设；广撒网的人自己把自己堵死。

**pending 的计算口径**：只统计 `status = 'pending'` 且 `created_at` 在 7 天内的记录。超过 7 天没人理的举手不再占额度，但也不改状态——这样既释放了额度，又保持了项目「过期靠查询实时判断、不引入定时任务」的既有约定（见 PRD 6 节对 `expires_at` 的处理）。UI 上把这类举手标为「已无回应」。

## 6. L4 定向频次

前三层都是按人总量算的，管不住「盯着一个人反复发」。这一层单独治骚扰。

| 约束 | 值 |
|---|---|
| 对同一用户发起举手（跨需求累计） | 2 次 / 天 |
| 同一条需求被拒后 | 7 天内不能再举手 |
| 同一条需求撤回后重发 | 累计不超过 3 次 |
| 举报同一目标 | 有 pending 时不可重复（已实现）；处理完成后 7 天冷却 |

**这里有一个必须堵的现存漏洞。** `app/actions/connections.ts:67` 的判断是：

```ts
if (existing && existing.status !== "rejected" && existing.status !== "cancelled") {
  return { error: "你已经举过手了" };
}
```

也就是说，被拒绝或自行撤回之后，可以对同一条需求无限次重新举手，每次都给发布者推一条通知。这是目前最容易被拿来骚扰人的口子，L4 的前三条就是为它准备的。

## 7. 承接侧（发布者）

发布者是被动方，滥用动机低，所以**不设日额度**，但有两处要管。

- **接受（accept）**：不限次数，但受 L3「已连接未完成 ≤ 10」约束。防的是把连接当通讯录囤着——接了不办，占着对方的存量额度不放。
- **拒绝（reject）**：完全不限。拒绝是健康行为，越顺手越好，任何摩擦都会让人转而选择"不理会"，而不理会对发起方是最差的结果（要挂满 7 天才释放额度）。
- **单条需求的举手容量**：同时 pending 的举手达到 **50** 时，该需求停止接收新举手，页面显示「这条需求收到的举手较多，暂不接收新的」。这一条同时保护两边——发布者不被淹没，攻击者也失去了刷爆某条热门需求的价值。

## 8. 额度赚回机制

纯静态额度对老实用户不公平：一个每次举手都被接受的人，和一个群发被全拒的人，享受同样的上限，没道理。加一层动态调整，让额度跟着行为质量走。

| 事件 | 效果 |
|---|---|
| 举手被接受 | 当日举手额度 +2 |
| 连接经双方确认完成 | 次日发布额度 +2、举手额度 +3 |
| 举手被拒绝 | 不返还 |
| 举手挂满 7 天无回应 | 释放存量额度，不返还日额度 |

单日累计加成不超过基础额度的 1 倍（举手最多 40，发布最多 20），避免出现"刷完成度换额度"的新玩法。

这条机制值得单拎出来说：**成本由行为质量支付，不由钱支付**。这是免费产品该有的样子——用得好的人几乎感觉不到额度存在，用得糙的人越刷越少。它比"付费解锁更多额度"更符合 We Match 的定位，因为后者本质上是在向滥用者出售滥用许可。

## 9. 惩罚阶梯

滥用信号累积后**自动降额，而不是封号**。封号误伤大、需要人工、还容易引发对抗；降额安静、可自动恢复、对误判的用户伤害有限。

| 信号 | 处置 | 时长 |
|---|---|---|
| 24 小时内被 3 个不同用户拉黑 | 举手日额度降为 3 | 7 天 |
| 24 小时内收到 3 条独立举报（不同举报人） | 发布日额度降为 2，并进人工审核队列 | 至处理完 |
| 举手接受率 < 5% 且样本 ≥ 20 | 举手日额度降为 5 | 直到接受率回升 |
| 管理员判定滥用 | 沿用现有 `users.status = 'suspended'` | 人工 |

`blocks`、`reports`、`connections` 三张表已经有全部数据，只差统计查询。降额期间用户可见提示，但不告知具体触发条件——说清楚了就等于给了绕过说明书。

## 10. 用户侧呈现

额度体系有一半是交互。用户撞墙才知道有额度，那额度就成了惩罚；提前知道，它才是规则。

呈现遵守 `docs/DESIGN.md`：计数属技术性内容，一律 `--mono`；额度提示不用焦橙（焦橙只给当屏主控件），走 `--gray`；撞墙的错误文案沿用现有 `text-accent` 错误样式，不新增颜色。

**1. 平时不显示。** 发布按钮和举手表单旁的剩余计数**只在剩余 ≤ 3 时出现**，形如 `剩余 2 / 10`。额度不该成为产品的主叙事——天天顶着计数器的产品，会诱导用户去想怎么把额度用完。

**2. 举手表单底部常驻一行状态**：`3 个等待回应中 · 还能举手 4 次`。这一处例外，因为 pending 存量是需要用户主动管理的东西，看不见就没法管。

**3. 撞墙时给出路，不只报错。** 每一条限制都要配一个具体的下一步：

| 撞到 | 文案 |
|---|---|
| 发布日额度 | 今天的 10 条已用完，明天 0 点恢复。也可以关掉几条已经完成的需求 → `我的 → 需求` |
| 发布存量 | 你有 20 条需求正在开放，先关掉一些再发新的 → `我的 → 需求` |
| 举手 pending 存量 | 有 5 个举手还在等回应。撤回一个，或等对方回应后再举手 → `我的 → 举手` |
| 同一人频次 | 今天已经联系过 TA 了，明天再试 |
| 被拒冷却 | 对方暂时没有接受，7 天后可以再举手 |
| 新账号降档 | 填好名片可以把每日发布额度提到 10 条 → `编辑名片` |

**4.「我的」页新增「额度」分类。** 复用现有的 `MeCategorySwitcher`，一屏列全今日剩余与存量占用，不新建页面（PRD 4.2 限死 10 个页面）。

## 11. 实现方案

### 落点：service 层，不是 action 层

现有开放 API（`app/api/v1/needs/route.ts`）和网页表单走的是同一个 `createNeed`，每日发布额度就在 `lib/needs-service.ts:154` 里，这个位置是对的。举手目前只有 Server Action、没有 API，但迟早会有——**额度检查一律放在 service 层**，网页和 API 共用同一份规则，避免出现"网页限了、API 没限"的绕过路径。

需要新建 `lib/connection-service.ts`，把 `app/actions/connections.ts` 里的业务逻辑抽下去。

### 两种计数方式，分工明确

- **L1 用 `rate_limits` 表**（现有 `consumeRateLimit`）。固定窗口、通用、无需实体记录。
- **L2 / L3 / L4 直接查实体表**。所有受限动作都已经在库里留了行（`needs` / `connections` / `reports` / `join_requests`），数出来就是准确值，不引入第二份状态，天然支持"赚回"（赚回即"不计入被接受的那条"），也天然对齐本地自然日——`rate_limits` 的固定窗口是按 epoch 对齐的，对不上 00:00。

现有发布额度已经是这个做法（`count(needs where createdAt >= dayStart)`），延续即可。

### 统一入口

```ts
// lib/quota.ts
export type QuotaKey =
  | "need.publish" | "need.refresh"
  | "connection.create" | "connection.accept"
  | "report.create" | "block.create"
  | "org.create" | "org.join";

export type QuotaDenial = {
  ok: false;
  reason: "throttle" | "daily" | "stock" | "target" | "penalty";
  message: string;                          // 直接展示给用户
  hint?: { href: string; label: string };   // 「出路」链接
};

export async function checkQuota(
  user: User,
  key: QuotaKey,
  target?: { userId?: number; needId?: number; orgId?: number },
): Promise<{ ok: true; remaining: number } | QuotaDenial>;

// 「我的 → 额度」页与各表单的剩余计数共用
export async function getQuotaSummary(user: User): Promise<QuotaSummary>;
```

调用侧每处一行：

```ts
const quota = await checkQuota(user, "connection.create", { userId: need.userId, needId });
if (!quota.ok) return { error: quota.message };
```

所有数值集中在 `lib/quota.ts` 的 `QUOTAS` 常量里，与 `NEED_LIMITS`、`ORG_LIMITS` 的现有风格一致，便于按线上数据调参。

### 需要补的索引

```sql
CREATE INDEX connections_initiator_created_idx ON connections(initiator_id, created_at);
CREATE INDEX connections_initiator_status_idx  ON connections(initiator_id, status);
CREATE INDEX needs_user_created_idx            ON needs(user_id, created_at);
CREATE INDEX reports_reporter_created_idx      ON reports(reporter_id, created_at);
```

「对同一用户举手次数」要 `connections join needs` 才能数出来（连接挂在需求上，不挂在人上）。数据量小的时候够用；如果慢了，再在 `connections` 上冗余一列 `target_user_id`。

### 不需要改的

- `rate_limits` 表结构不动，L1 直接复用。
- 不加定时任务。7 天无回应的举手靠查询条件实时判断，与需求过期的处理方式保持一致。

## 12. 落地顺序

| 阶段 | 内容 | 理由 |
|---|---|---|
| P0 | L4 的三条 + 举手 pending 存量 ≤ 5 | 补现在真实存在的骚扰漏洞，一天能改完 |
| P1 | `lib/quota.ts` + L1 + L2 全量 + 撞墙文案 | 体系主干 |
| P2 | 新账号分档 + L3 剩余部分 + 「我的 → 额度」 | 需要 UI 配合 |
| P3 | 赚回机制 + 惩罚阶梯 | 依赖线上数据调参，先跑一段时间看真实分布 |

P3 之前，所有数值都按本文的保守值写死；上线两周后拉一次 `analytics_events` 的分布，看 P95 用户实际用到多少，再决定松紧。**调参的依据是分布，不是感觉。**

## 13. 待确认

1. **举手日额度 20 是否偏高**？如果广场规模小（比如几百人），20 次意味着一个人一天能碰所有活跃需求，或许 10 更合适。
2. **接受举手是否应该解锁额外信息**？目前联系方式完全由名片可见性控制，与连接状态无关。如果以后改成「接受后才给联系方式」，举手额度要立刻收紧（那时举手就成了套联系方式的手段，滥用价值大得多）。
3. **API Key 数量上限**：现有每 Key 120 次/分钟，但没限制一个人能建几个 Key。建议 5 个，否则限流可以靠多开 Key 绕过。
4. **组织内是否放宽额度**？组织是熟人圈，滥用风险低于广场。可以考虑组织内发布和举手单独计一份额度，或者按 1.5 倍放宽。
