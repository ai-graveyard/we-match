# We Match 交互额度体系

- 版本：v2.0（设计稿）
- 日期：2026-08-07
- 状态：P0–P4 全部落地。P1 揭示模型与 P2 `lib/quota.ts` 随 M6 上线；P3（「我的 → 额度」、剩余 ≤ 3 提示、举手表单常驻计数、「已无回应」）与 P4（赚回、惩罚阶梯）随后补齐。**惩罚阶梯默认 shadow 模式**（`QUOTA_P4_MODE`，只观测不降额），见第 10 节。数值仍是本文的保守值，上线两周后按 `analytics_events` 分布调参
- 前置决定：**联系方式在举手被接受后才交换**（v1.0 假设联系方式由名片可见性直接控制，已作废）

## 1. 这套额度在保护什么

We Match 免费，注册只要一个邮箱。这两件事凑在一起，把发布和举手的边际成本压到接近零——对正常用户是好事，对刷子也是。

**2026-08-08 起身份从手机号换成邮箱**（理由见 `AGENT-FIRST.md` 第 10 节），本层的压力因此变大：手机号实名、要花钱、数量有限，邮箱可以无限申请。这是知情取舍——本文的四层结构原本就不依赖「一人一号」，它拦的是**行为**不是身份：L3 存量额度和 L4 定向频次照样对每个新开的号单独生效，刷子多开一个号并不能让手上那 5 个 pending 举手变多。真正被削弱的只有 L2 日额度那一档，对策见第 5 节。

但「接受后才交换联系方式」这个决定，让额度要保护的东西变了。原来广场上最值钱的是曝光位，现在最值钱的是**联系方式本身**。这带来一条全新的、也是最危险的滥用路径：

> 发一条诱饵需求 → 坐等举手 → 全部接受 → 一次收割几十个联系方式。

成本极低：一条需求就够，剩下的是点几下接受。一天 10 条诱饵需求、每条 50 个举手，就是 500 份联系方式。而在原来的模型里，这条路径根本不存在——联系方式本来就对登录用户开放，没什么好收割的。

所以这一版的重点变化是：**承接侧从"不设额度"改为"必须设额度"**。接受不再是一个状态标记，它是一次授权动作，跟发短信、发邮件一样要算成本。

定额原则不变，只有一条：

> **95% 的正常用户永远碰不到上限，刷子第一小时就撞墙。**

不设付费扩容。超额的唯一解法是把手上的事做完——一旦开了充值扩容的口子，等于向滥用者出售滥用许可，整套设计的正当性就没了。

## 2. 揭示模型（额度之前先定清楚这个）

额度限制的是「揭示」这个动作，所以得先说清楚一次接受到底给出去什么。

### 2.1 交换是双向的，但只给一项

接受后双方互换联系方式，**各自只给一项，不是全部字段**。

- 发布者给出的是该需求的 `preferredContact`（这个字段已经是必填，见 PRD 3.3）；
- 举手方在举手时从自己名片上选一项，作为交换物。

只给一项，是压低收割价值最有效的一招。收割 500 个微信号和收割 500 份完整档案（微信 + 手机 + 邮箱 + 四个社媒）完全是两码事，后者可以直接拿去卖。

举手表单因此要多一个联系方式选择器，默认取名片上第一项可用的。这顺带解决了一个知情同意问题：用户在**点举手之前**就看见「接受后对方将看到你的微信号」，而不是事后才发现给出去了什么。

### 2.2 名片上必须还留着足够判断的信息

新模型有一个致命的自我拆台风险：**如果名片什么都看不到，用户凭什么举手？**

举手是有成本的（占额度、要等回应），用户必须能在举手前判断值不值。所以联系方式收进连接制的同时，其余信息要保持开放：

| 字段 | 档位 | 理由 |
|---|---|---|
| 昵称、一句话介绍、标签、城市 | 公开 | 判断"这人靠不靠谱"的全部依据 |
| 微信公众号、视频号、小红书、微博 | 登录可见 | 这些本来就是对外公开的账号，是作品和身份展示，不是联系方式 |
| **微信号、手机号、邮箱** | **连接后可见** | 真正的私人联系方式，走连接制 |

社媒和联系方式必须分开处理。社媒是"我是谁"，联系方式是"怎么找到我"——前者藏起来只会让人无从判断，后者藏起来才是保护。

### 2.3 可见性档位要加一档

现有三档 `authenticated` / `orgs` / `hidden`，需要新增 `connected`：

| 档位 | 含义 | 用在哪 |
|---|---|---|
| `authenticated` | 任意登录用户可见 | 社媒默认；也留给主动想被随便联系的人（自由职业者、招人的） |
| `orgs` | 共同组织成员可见 | 组织是熟人圈，成员间不必走举手 |
| `connected` | **举手被接受后可见** | 联系方式的新默认档 |
| `hidden` | 谁都看不见 | 不变 |

**迁移方向必须是收紧。** 现存数据里联系方式默认是 `authenticated`（`fieldVisibility` 未记录时的缺省，见 `lib/db/schema.ts:10` 的注释），升级后一律按 `connected` 解释。这和 PRD 6 节处理历史 `public` 值的思路一致——升级时只往严了走，不能让任何人的联系方式在不知情的情况下保持开放。

用户可以主动改回 `authenticated`，但那必须是他自己点的。

### 2.4 组织内不走连接制

组织成员之间用 `orgs` 档直接可见，举手在组织内只是意向表达，不承担揭示功能。组织有审批门槛，本身就是熟人关系，再加一道举手是多余的摩擦。

这也顺带给了整个改动一个对照组：组织内的流程完全不变，出问题可以对比。

### 2.5 揭示无法撤销，要说实话

已经看到的东西收不回来。撤回连接、拉黑之后页面上不再显示，但对方可能早就复制走了。UI 上必须直说：「接受后对方将看到你的微信号，已看到的内容无法收回」。含糊其辞比什么都不说更糟。

每次揭示落一条 `contact_reveals` 记录（谁、给谁、哪个字段、哪条需求、什么时候）。这是事后追查收割行为的唯一依据，也是举报处理时的证据。
删除需求或解散组织只撤下内容，不得删除这条记录及其关联的连接、需求审计行；否则删除后即可重置额度并抹掉调查证据。撤回、拉黑、需求删除后读路径不再展示联系方式，但台账继续保留。

## 3. 四层结构

单一维度必然被绕开：只限每天条数，刷子就天天顶格；只限速度，刷子就慢慢刷。四层各管一类滥用，缺一层漏一类。

| 层 | 管什么 | 时间尺度 | 正常用户感知 |
|---|---|---|---|
| L1 节流 | 机器连点 | 秒 | 无 |
| L2 日额度 | 单日灌水与单日收割 | 自然日 | 极少 |
| L3 存量额度 | 长期囤积 | 无期限 | 偶尔 |
| L4 定向频次 | 盯人骚扰 | 天 / 周 | 无 |

L3 是现在完全缺失的一层，也是最重要的一层。日额度只管流入速度：一天 10 条，一个月就是 300 条挂在广场上，日额度对此毫无办法。真正决定广场好不好用的是"此刻同时占着多少"。

## 4. L1 节流

统一走现有的 `consumeRateLimit`（`lib/rate-limit.ts`，SQLite 固定窗口，重启和多进程都不清零）。纯粹拦脚本，正常人手速够不到。

| 动作 | 限制 |
|---|---|
| 发布需求 | 1 次 / 30 秒 |
| 发起举手 | 1 次 / 20 秒 |
| **接受举手** | **1 次 / 10 秒** |
| 提交举报 | 1 次 / 60 秒 |
| 组织加入申请 | 1 次 / 60 秒 |
| 编辑需求 / 名片 | 1 次 / 5 秒 |
| 任意写操作（按用户兜底） | 30 次 / 分钟 |

接受加节流是新的：批量收割必然表现为连点接受，10 秒一次能让收割 50 个人至少花 8 分钟，配合日额度就基本不成立了。

撞到 L1 一律回同一句「操作太快，请稍后再试」，不说具体窗口——说清楚等于告诉脚本该 sleep 多久。

## 5. L2 日额度

自然日 00:00（服务器本地时区）重置，与现有发布额度算法一致。

**分两档。** 新账号降档是这一层的关键：注册成本低，刷子必然批量开号，让新号第一天额度砍到三分之一，等于把开号成本抬高三倍。

换成邮箱后开号成本进一步降低，这一档被削弱得最明显。**暂不加码**（不做一次性邮箱黑名单、不做邮箱账号降档双轨），理由是转正门槛的第 2 条本身就是过滤器：刷子要拿满额度得先把名片填成一张能判断、能联系的卡，而那正是我们想要的东西。真出现批量开号再上黑名单。

| 动作 | 新账号 | 常规账号 | 相比 v1.0 |
|---|---|---|---|
| 发布需求 | 3 | 10 | 不变 |
| **发起举手** | **3** | **8** | **20 → 8，砍掉六成** |
| **接受举手** | **5** | **20** | **新增** |
| 提交举报 | 3 | 10 | 不变 |
| 组织加入申请 | 2 | 5 | 不变 |
| 创建组织 | 1 | 2 | 不变 |
| 需求续期 | 5 | 20 | 不变 |
| 拉黑 | 20 | 50 | 不变 |
| 编辑名片 | 30 | 50 | 不变 |

**举手从 20 砍到 8**：举手现在是"申请交换联系方式"，不再是随手点个赞。认真找人的一天举手 1 到 2 次，8 次已经宽裕到不讲理；广撒网的会立刻感到疼。

**接受 20 次/天**：正常发布者一天接受 2 到 3 个就够了，20 是给招人、办活动这类真实高频场景留的余量。但它同时把单日收割上限钉死在 20 份联系方式——不是不能收割，是收割效率低到不值得。

**另加一条兜底**：任何用户单日作为提供方被揭示的次数不超过 **30**。这道闸门跨越所有路径（自己接受别人 + 别人接受自己），防的是我们没想到的组合玩法。

### 升为常规账号需同时满足

1. 注册满 72 小时；
2. 名片填了一句话介绍、至少 1 个标签、至少 1 项可用的联系方式。

第 2 条顺手做了件好事：想要完整额度，先把名片填好。既提高刷子成本，又让广场上活跃的人都是能判断、能联系的人。UI 写成正向引导而不是惩罚——「填好名片，每日发布额度从 3 提到 10」，配直达「编辑名片」的链接。

## 6. L3 存量额度

不看时间窗口，只看此刻手上占着多少。用完不自动恢复，只能靠把事情做完来释放。

| 存量 | 上限 | 释放方式 |
|---|---|---|
| 同时开放的需求（open 且未过期） | 20 | 标记完成 / 关闭 / 自然到期 |
| **等待回应的举手（pending）** | **5** | 被接受 / 被拒 / 自行撤回 / 需求关闭 / 挂满 72 小时 |
| 已连接未完成（accepted） | 10 | 双方确认完成 / 撤回 |
| **未处理的举手（作为发布者）** | **10** | 处理掉（接受或拒绝） |
| 待审批的组织申请 | 3 | 管理员处理 |

### 「等待回应的举手 ≤ 5」是核心阀门

它不需要任何判别逻辑就区分开两类人：认真找人的同时盯 2 到 3 个机会，一辈子碰不到；群发的第 6 个就卡住，**而且他的速度被他打扰的人的耐心接管了**。

日额度 8 依然在，但实际能不能用满，取决于前面的举手有没有回音。这是个自我调节的机制：举手质量高的人流转快，额度形同虚设；广撒网的人自己把自己堵死。

**pending 口径**：只统计 `status = 'pending'` 且 `created_at` 在 **72 小时**内的记录。v1.0 定的是 7 天，新模型下必须缩短——原来不回应无所谓（联系方式本来就能看到），现在不回应意味着举手方彻底拿不到东西，还白占着额度。72 小时后自动释放额度但不改状态，保持项目「过期靠查询实时判断、不引入定时任务」的既有约定（PRD 6 节对 `expires_at` 的处理同理）。UI 上把这类举手标为「已无回应」。

### 「未处理举手 ≥ 10 就不能发新需求」

这是新模型下必须加的反向压力。发布者不回应，代价全部由举手方承担（占着额度干等 72 小时），发布者自己毫无损失——这个不对称必须扳平。

规则很简单：**手上攒着 10 个没处理的举手，就发不了新需求**。想继续发，先把手上的处理完，接受还是拒绝都行。它完全不影响认真的用户（认真的人本来就会处理），但让"发了不管"变得不可持续。

**配套规则（已实现，先于本体系其余部分落地）：存在超过 72 小时未处理的举手时，不能续期任何需求**（`lib/needs-service.ts` 的 `applyNeedPatch` 统一拦截：延长截止、改永久、重开都算续命；网页与 API 同规则，API 返回 422 `renewal_blocked`，测试见 `tests/renewal-lock.test.ts`）。数量闸门管「攒太多」，这条时间闸门管「彻底不理」。它同时是 Agent-first 的结构防线：举手处理必须由人在网页完成，把它设为续期的前置条件，等于要求续期背后有人类心跳——用户失联后，他的 Agent 拿不到续期许可，帖子在一个续期周期内自然过期下架，广场靠这条自清洁（背景见 AGENT-FIRST.md 7.3）。拒绝不限额度、不设冷却，处理一下就解除，正常用户几乎无感。

## 7. L4 定向频次

前三层都按人的总量算，管不住"盯着一个人反复发"。这一层单独治骚扰。

| 约束 | 值 |
|---|---|
| 对同一用户发起举手（跨需求累计） | 2 次 / 天 |
| 同一条需求被拒后 | 7 天内不能再举手 |
| 同一条需求撤回后重发 | 累计不超过 3 次 |
| 举报同一目标 | 有 pending 时不可重复（已实现）；处理完成后 7 天冷却 |

**这里有一个必须堵的现存漏洞。** `app/actions/connections.ts:67` 的判断是：

```ts
if (existing && existing.status !== "rejected" && existing.status !== "cancelled") {
  return { error: "你已经举过手了" };
}
```

被拒绝或自行撤回之后，可以对同一条需求无限次重新举手，每次都给发布者推一条通知。这在原模型下已经是骚扰口子，在新模型下更糟——被拒的人有了明确动机反复试，因为拿到联系方式是有实际收益的。L4 前三条就是为它准备的。

## 8. 承接侧（这一节相比 v1.0 完全重写）

v1.0 的判断是「发布者是被动方，滥用动机低，不设日额度」。这个判断在新模型下彻底失效——接受现在是发放行为，是整套体系里最需要管的动作。

| 动作 | 限制 | 防什么 |
|---|---|---|
| 接受 | 20 次/天（新号 5）、1 次/10 秒 | 单日收割量 |
| **单条需求累计接受** | **10** | 诱饵需求 |
| 已连接未完成 | ≤ 10（L3） | 接了不办，占着对方额度 |
| 拒绝 | 完全不限 | —— |

**「单条需求累计接受 ≤ 10」比日额度更精准。** 收割必然集中在少数几条诱饵需求上——"免费送""内推名额""资源对接"这类帖子一条能吸几十个举手。正常需求呢？"我需要一个前端"接受 3 个已经够挑了，10 个是给招聘、组队这类场景留的余量。达到 10 之后该需求停止接收新举手，页面显示「这条需求收到的举手较多，暂不接收新的」，两边都保护到了。

**拒绝完全不限，而且要做得比接受更顺手。** 拒绝是健康行为，任何摩擦都会让发布者转向"不理会"，而不理会是对举手方最差的结果（白等 72 小时），L3 的存量额度也会大量卡死在无效 pending 上。按钮位置、点击次数都不能让拒绝比接受麻烦——这条已经写进 [DESIGN.md](DESIGN.md)「举手与连接」当硬规范，它看着像交互细节，其实是额度体系的一部分。

## 9. 额度赚回机制

纯静态额度对老实用户不公平：每次举手都被接受的人，和群发被全拒的人，享受同样的上限，没道理。加一层动态调整，让额度跟着行为质量走。

| 事件 | 效果 |
|---|---|
| 举手被接受 | 当日举手额度 +2 |
| 连接经双方确认完成 | 次日发布额度 +2、举手额度 +3 |
| 举手被拒绝 | 不返还 |
| 举手挂满 72 小时无回应 | 释放存量额度，不返还日额度 |
| **及时处理举手（24 小时内）** | **当日接受额度 +1** |

单日累计加成不超过基础额度的 1 倍（举手最多 16，接受最多 40，发布最多 20），避免出现"刷完成度换额度"的新玩法。

最后一条是新加的：奖励**处理速度**，不奖励接受本身。奖励接受等于变相补贴收割；奖励"接受或拒绝都算处理"，才是在鼓励发布者别晾着人。

这条机制值得单拎出来说：**成本由行为质量支付，不由钱支付**。用得好的人几乎感觉不到额度存在，用得糙的人越刷越少。它比付费解锁更符合免费产品的定位，也是这套设计里唯一能长期自我调节的部分。

## 10. 惩罚阶梯

滥用信号累积后**自动降额，而不是封号**。封号误伤大、需要人工、容易引发对抗；降额安静、可自动恢复、误判代价有限。

| 信号 | 处置 | 时长 |
|---|---|---|
| **7 日接受量 > 30 且接受率 > 90%** | **接受日额度降为 3，进人工队列** | 至处理完 |
| **单条需求举手数 > 30 且接受率 > 80%** | **该需求停止接收举手，进人工队列** | 至处理完 |
| 24 小时内被 3 个不同用户拉黑 | 举手日额度降为 3 | 7 天 |
| 24 小时内收到 3 条独立举报（不同举报人） | 发布日额度降为 2，进人工队列 | 至处理完 |
| 举手接受率 < 5% 且样本 ≥ 20 | 举手日额度降为 5 | 直到接受率回升 |
| 管理员判定滥用 | 沿用现有 `users.status = 'suspended'` | 人工 |

前两条是新模型的核心检测项。**正常发布者的接受率应该在 20% 到 60% 之间**——挑人本来就要拒掉一些。一个接受率 95%、接受量 40 的账号，几乎必然是在收割：他根本不在乎举手的是谁。

`blocks`、`reports`、`connections` 三张表已经有全部数据，只差统计查询。降额期间给用户可见提示，但不告知具体触发条件——说清楚就等于给了绕过说明书。

**默认影子模式（shadow）。** 惩罚阶梯的执行由 `QUOTA_P4_MODE` 控制，默认 `shadow`：照常计算候选降额，但**不真正压低用户额度**，只在用户达到「若 enforce 就会被拦截」的量时写一条限频（同用户/动作/天一条）的 `quota_penalty_shadow` 分析事件。这样能先在真实流量上核对阈值是否误伤，再由运营切到 `enforce` 才真正降额。`effectiveDailyLimit` 因此区分「已执行降额」（`penalty`，UI 与拦截文案只认它）与「候选降额」（`shadowPenalty` / `shadowLimit`，仅供观测）；shadow 下用户界面不会看到任何降额提示。

## 11. 用户侧呈现

额度体系有一半是交互。撞墙才知道有额度，额度就是惩罚；提前知道，它才是规则。

呈现遵守 `docs/DESIGN.md`：计数属技术性内容，一律 `--mono`；额度提示不用焦橙（焦橙只给当屏主控件），走 `--gray`；撞墙错误沿用现有 `text-accent` 错误样式，不新增颜色。

**1. 平时不显示。** 发布按钮和举手表单旁的剩余计数**只在剩余 ≤ 3 时出现**，形如 `剩余 2 / 8`。额度不该成为产品的主叙事——天天顶着计数器的产品会诱导用户去想怎么把额度用完。

**2. 三处常驻例外**，因为它们是用户需要主动管理的：

- 举手表单底部：`3 个等待回应中 · 还能举手 4 次`
- 举手表单里的交换预告：`接受后对方将看到你的微信号`（带切换入口）
- 「我的」页顶部，未处理举手 ≥ 5 时：`8 个举手等你处理`，直达列表

**3. 撞墙时给出路，不只报错。**

| 撞到 | 文案 |
|---|---|
| 发布日额度 | 今天的 10 条已用完，明天 0 点恢复。也可以关掉几条已完成的需求 → `我的 → 需求` |
| 发布存量 | 你有 20 条需求正在开放，先关掉一些再发新的 → `我的 → 需求` |
| **未处理举手卡住发布** | **有 8 个举手在等你回应，处理完就能继续发布** → `我的 → 额度` |
| **超时未处理举手卡住续期** | **有举手等你回应超过 3 天了，处理完就能续期** → `我的 → 额度` |
| 举手 pending 存量 | 有 5 个举手还在等回应。撤回一个，或等对方回应后再举手 → `我的 → 额度` |
| **接受日额度** | **今天已经接受 20 个举手，明天 0 点恢复** |
| **单需求接受上限** | **这条需求已经连上 10 个人，如果还要找人，建议新发一条** |
| 同一人频次 | 今天已经联系过 TA 了，明天再试 |
| 被拒冷却 | 对方暂时没有接受，7 天后可以再举手 |
| 新账号降档 | 填好名片可以把每日发布额度提到 10 条 → `编辑名片` |

**4.「我的」页新增「额度」分类。** 复用现有 `MeCategorySwitcher`，一屏列全今日剩余与存量占用，不新建页面（PRD 4.2 限死 10 个页面）。它同时兼任「我的 → 举手」：底部列出等你处理的举手，超过 72 小时的标出来并直达需求详情——本文各处写作「我的 → 举手」的出路都指这里。

## 12. 实现方案

### 落点：service 层，不是 action 层

现有开放 API（`app/api/v1/needs/route.ts`）和网页表单走同一个 `createNeed`，每日发布额度就在 `lib/needs-service.ts:154`，位置是对的。举手目前只有 Server Action、没有 API，但迟早会有——**额度检查一律放 service 层**，网页和 API 共用一份规则，不留"网页限了 API 没限"的绕过路径。

需要新建 `lib/connection-service.ts`，把 `app/actions/connections.ts` 的业务逻辑抽下去。揭示逻辑也放这里，绝不能散落在页面组件里。

### 两种计数方式，分工明确

- **L1 用 `rate_limits` 表**（现有 `consumeRateLimit`）：固定窗口、通用、无需实体记录。
- **L2 / L3 / L4 直接查实体表**：所有受限动作都已在库里留了行（`needs` / `connections` / `reports` / `join_requests` / 新增 `contact_reveals`），数出来就是准确值，不引入第二份状态，天然支持"赚回"，也天然对齐本地自然日（`rate_limits` 的固定窗口按 epoch 对齐，对不上 00:00）。

现有发布额度已经是这个做法（`count(needs where createdAt >= dayStart)`），延续即可。

### 统一入口

```ts
// lib/quota.ts
export type QuotaKey =
  | "need.publish" | "need.refresh"
  | "connection.create" | "connection.accept"
  | "report.create" | "block.create"
  | "org.create" | "org.join";

export type QuotaDenial = {
  ok: false;
  reason: "throttle" | "daily" | "stock" | "target" | "penalty" | "backlog";
  message: string;                          // 直接展示给用户
  hint?: { href: string; label: string };   // 「出路」链接
};

export async function checkQuota(
  user: User,
  key: QuotaKey,
  target?: { userId?: number; needId?: number; orgId?: number },
): Promise<{ ok: true; remaining: number } | QuotaDenial>;

export async function getQuotaSummary(user: User): Promise<QuotaSummary>;
```

调用侧每处一行：

```ts
const quota = await checkQuota(user, "connection.accept", { needId });
if (!quota.ok) return { error: quota.message };
```

所有数值集中在 `lib/quota.ts` 的 `QUOTAS` 常量，与现有 `NEED_LIMITS`、`ORG_LIMITS` 风格一致，便于按线上数据调参。

### 数据库改动

```sql
-- 举手方选定的交换物
ALTER TABLE connections ADD COLUMN initiator_contact TEXT;  -- wechat|email|contactPhone

-- 揭示台账：收割行为的事后追查依据
CREATE TABLE contact_reveals (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  connection_id INTEGER NOT NULL REFERENCES connections(id),
  need_id       INTEGER NOT NULL REFERENCES needs(id),
  from_user_id  INTEGER NOT NULL REFERENCES users(id),  -- 联系方式的主人
  to_user_id    INTEGER NOT NULL REFERENCES users(id),  -- 看到的人
  field         TEXT    NOT NULL,                        -- wechat|email|contactPhone
  created_at    INTEGER NOT NULL
);
CREATE INDEX contact_reveals_from_created_idx ON contact_reveals(from_user_id, created_at);
CREATE INDEX contact_reveals_to_created_idx   ON contact_reveals(to_user_id, created_at);

-- 额度统计
CREATE INDEX connections_initiator_created_idx ON connections(initiator_id, created_at);
CREATE INDEX connections_initiator_status_idx  ON connections(initiator_id, status);
CREATE INDEX connections_need_status_idx       ON connections(need_id, status);
CREATE INDEX needs_user_created_idx            ON needs(user_id, created_at);
CREATE INDEX reports_reporter_created_idx      ON reports(reporter_id, created_at);
```

`field_visibility` 的类型要加 `connected`（`lib/db/schema.ts:12`），读取时把历史 `authenticated` 值按 `connected` 降级——**只往严了走**。

「对同一用户举手次数」要 `connections join needs` 才数得出来（连接挂在需求上，不挂在人上）。数据量小时够用；慢了再在 `connections` 冗余一列 `target_user_id`。

### 不需要改的

- `rate_limits` 表结构不动，L1 直接复用。
- 不加定时任务。72 小时无回应的举手靠查询条件实时判断，与需求过期处理方式一致。

## 13. 落地顺序

| 阶段 | 内容 | 理由 |
|---|---|---|
| P0 | L4 三条 + 举手 pending ≤ 5 | 补现存的骚扰漏洞，与揭示模型无关，可以立刻做 |
| P1 | 揭示模型：`connected` 档 + 数据迁移 + `contact_reveals` + 举手交换选择器 | 新模型的地基，必须整块上 |
| P2 | `lib/quota.ts` + L1 + L2 全量 + 承接侧全套 + 撞墙文案 | 体系主干 |
| P3 | 新账号分档 + L3 剩余部分 + 「我的 → 额度」 | 需要 UI 配合 |
| P4 | 赚回机制 + 惩罚阶梯 | 依赖线上数据调参 |

五个阶段都已落地。实现落点：额度全在 [`lib/quota.ts`](../lib/quota.ts)（`checkQuota` 判定、`effectiveDailyLimit` 算赚回与降额、`getQuotaSummary` 供 UI），举手写路径在 [`lib/connections-service.ts`](../lib/connections-service.ts)，举报/拉黑写路径在 [`lib/safety-service.ts`](../lib/safety-service.ts)，回归用例见 `tests/quota.test.ts` 与 `tests/safety.test.ts`。

两个实现上值得记的决定：

- **每日举手计数看 `connections.last_raised_at`，不看 `updated_at`。** 后者会被对方的接受/拒绝改写，拿它计数等于把别人的动作记到举手方头上。列由 `drizzle/0010_quota-p3p4.sql` 加上，存量行回填 `created_at`。
- **降额不落新表，全靠查实体表实时算。** 「24 小时内被 3 人拉黑 → 降额 7 天」用滑动窗口扫惩罚期内的拉黑时刻；「3 条独立举报 → 至处理完」只看仍 pending 的举报，管理员处理掉即自动恢复。没有第二份状态要维护，也不需要定时任务。

**P1 必须整块上线，不能分批。** 可见性档位改一半会出现"有人的联系方式已收紧、有人还开放着"的中间态，隐私上不可接受。

P4 之前所有数值按本文保守值写死。上线两周后拉一次 `analytics_events` 分布，看 P95 用户实际用到多少再调松紧。**调参依据是分布，不是感觉。** 惩罚阶梯默认 `shadow`，先用 `quota_penalty_shadow` 事件核对候选降额是否误伤真实用户，确认后再切 `enforce`。
