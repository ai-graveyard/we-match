# We Match 交互额度体系

- 版本：v2.1
- 核对日期：2026-10-03
- 状态：发布、举手、接受、举报、拉黑、组织额度及赚回/日额度惩罚已实现。本文区分实际规则与原设计未落地项，不代表线上配置已验收。
- 实现源：[`lib/quota.ts`](../lib/quota.ts)、[`lib/connections-service.ts`](../lib/connections-service.ts)、[`lib/needs-service.ts`](../lib/needs-service.ts)。

## 1. 目标与边界

限制批量发布、囤积未处理连接、骚扰和联系方式收集。不设付费扩容；网页与 Agent 使用同一用户额度。平台只召回候选，举手、接受、拒绝由人在网页完成，v1 没有对应写端点。

原设计中的四层为秒级节流（L1）、日额度（L2）、存量（L3）和定向频次（L4）。当前实现覆盖下列动作，未实现的通用规则列在第 12 节。

## 2. 揭示与可见性

接受举手时，发布者提供需求的 `preferredContact`，举手方提供自己选择的联系方式；双方各一项，在同一个 SQLite `IMMEDIATE` 事务中更新连接并写两条 `contact_reveals`。

联系方式默认 `connected`，用户可主动改为 `authenticated`（登录可见）、`orgs`（共同组织可见）或 `hidden`。基本资料默认公开且可隐藏（昵称始终公开），社媒默认登录可见。迁移 `0009_m6-connection.sql` 增加连接字段与揭示表，不改存量可见性 JSON；历史缺省/旧 public 联系方式由读规则收紧为 connected，显式 `authenticated` 保留，不能每次读取都再改回 `connected`。

组织内 `orgs` 字段可直接查看，但 `connected` 仍需交换。组织内举手同样走联系方式选择、接受、揭示与额度，不存在独立的免额度组织连接流程。

名片按双方所有有效连接汇总已揭示字段，并结合字段当前可见性过滤；一次交换不会开放整张名片。撤回、拉黑或删除关联需求后，相关揭示不再用于显示；对方已复制的内容无法收回。删除需求和解散组织保留需求、连接、揭示台账，仅撤下用户可读内容。

## 3. L1 秒级节流

使用 `consumeRateLimit` 的 SQLite 固定窗口，重启不清零；Vitest 环境跳过 `denyIfThrottled`，故领域单测不证明真实请求冷却行为。

| 动作 | 已实现限制 |
| --- | --- |
| 发布需求 | 1 次 / 30 秒 |
| 发起举手 | 1 次 / 20 秒 |
| 接受举手 | 1 次 / 10 秒 |
| 提交举报 | 1 次 / 60 秒 |
| 组织加入申请 | 1 次 / 60 秒 |

创建组织和拉黑有日额度，没有上述秒级节流。拒绝不做额度或冷却限制。编辑/续期和所有写操作的统一兜底见第 12 节。

API 另有每 Key 每分钟 120 次请求限制；`/auth/*` 每 IP 每小时 20 次，叠加验证码每邮箱 60 秒一次、每 IP 每小时 10 条。这些与业务额度独立。

## 4. L2 基础日额度

按服务器本地自然日 00:00 重置（`dayStart`），不是访问者时区。部署时应明确服务器时区。

| 动作 | 新账号 | 常规账号 |
| --- | --- | --- |
| 发布需求 | 3 | 10 |
| 发起举手 | 3 | 8 |
| 接受举手 | 5 | 20 |
| 提交举报 | 3 | 10 |
| 组织加入申请 | 2 | 5 |
| 创建组织 | 1 | 2 |
| 拉黑 | 20 | 50 |

常规账号须同时满足注册满 72 小时、简介非空、至少一个标签、至少一项已填联系方式。当前 `isRegularAccount` 只检查联系方式有值，不检查其可见档位；发布时另外执行可联系性校验。

发布/举手/接受的实际日额度会受第 8 节赚回及第 10 节执行降额影响，不能把基础额度写成绝对最大值。

另有接受时的提供方揭示日上限 30：当前接受路径只核对执行接受的发布者当天作为提供方的揭示数，没有同时对举手方做对称校验；因此不能宣称双方所有路径都被统一限制在 30 次内。

## 5. L3 存量

| 项目 | 当前限制与计数口径 |
| --- | --- |
| 同时开放需求 | 20；未删除、open 且未过期，完成/关闭/到期/删除释放 |
| 发起的 pending 举手 | 5；需求未删除、pending 且 createdAt 在 72 小时内。接受/拒绝/撤回/满 72 小时/需求删除释放；仅关闭需求不直接释放 |
| accepted 未完成连接 | 10；按双方身份合计未删除需求上的 accepted。当前在发起新举手时检查，接受路径未检查双方该存量 |
| 发布者未处理举手 | 达到 10 时阻止新发布；统计未删除需求全部 pending，包含超过 72 小时的记录 |
| 待审批组织申请 | 3；pending 申请数，与同时加入最多 3 个组织的成员名额是两项规则 |

pending 满 72 小时不会自动修改状态；界面显示「已无回应」，释放发起方存量，但发布者仍需处理。与需求自然到期一样由查询判断，无定时任务。

## 6. 续期锁

用户有超过 72 小时未处理的收到举手时，`applyNeedPatch` 拒绝延长截止时间、改永久或重开任何需求。网页与 API 共享规则，API 返回 422 `renewal_blocked`。

缩短截止时间、关闭、标完成和只改内容不受此锁限制。引导用户到 `/me/connections` 处理收到的举手；「我的 → 额度」也提供入口。拒绝不耗额度，不能引导 Agent 重试绕过。

空 PATCH `{}` 将截止时间设为一个月后，但不自动把 closed/done 状态改回 open。当前没有独立的续期日额度。

## 7. L4 定向频次与单需求上限

| 约束 | 当前值 |
| --- | --- |
| 对同一用户举手，跨需求累计 | 2 条记录 / 天，按 lastRaisedAt 统计 |
| 同需求被拒后再次举手 | 7 天冷却 |
| 撤回后重新举手 | 撤回状态下，已有 raiseCount 达到 4（首发 + 3 次重发）即拒绝；拒绝后的重发主要受 7 天冷却限制 |
| 举报同一目标 | pending 时不重复；处理完成后 7 天冷却 |
| 单条需求接受数 | 10；当前状态为 accepted/completed 的连接数，发起与接受均检查 |

同一 `(need_id, initiator_id)` 只有一条连接记录，重发原地复用并递增 `raiseCount`、更新 `lastRaisedAt`，不重置 `createdAt`；72 小时 pending 口径仍使用首次创建时间。单条需求上限并非不可回退的历史累计数：已撤回连接不计入该 accepted/completed 计数；揭示台账仍保留。

## 8. 额度赚回

| 事件 | 加成 |
| --- | --- |
| 本人举手当日被接受 | 当日举手 +2 |
| 双方确认完成 | 次日发布 +2、举手 +3 |
| 24 小时内处理举手（接受或拒绝） | 当日接受 +1 |
| 拒绝或满 72 小时无回应 | 不返还当日日额度；状态变化/超时可释放相应存量 |

总额度最多基础值两倍。常规账号上限为发布 20、举手 16、接受 40；新账号分别为 6、6、10。执行惩罚时使用惩罚额度，赚回不能抵消。

这些加成按当前连接记录计算，不是独立不可变奖励账本。及时处理使用 `updatedAt - createdAt` 判定，后续更新同一连接可能影响计数。

## 9. 计数与持久化

L1 使用 `rate_limits`；日额度、存量、定向频次和赚回查询实体表。关键口径：

- 发布日计数包含已软删除需求，删除不能恢复发布名额。
- 举手日计数看 `lastRaisedAt`，不看会被接受/拒绝改写的 `updatedAt`；按记录数计，不是每次重发的独立事件数。当前本人日计数排除已删除需求，同目标计数不排除。
- 接受日计数使用当前 accepted/completed 状态和 `acceptedAt`；撤回会使这项计数变化。
- 揭示日计数直接数 `contact_reveals`；删除需求/解散组织不删除这些记录。
- 举报、组织、加入申请、拉黑从各自实体表计数，没有统一不可变动作账本。

接受与双向揭示、发起举手的关键计数重查和写入共用同步 `IMMEDIATE` 事务。不要在 better-sqlite3 事务回调里 `await`。

## 10. 惩罚阶梯与 shadow

`effectiveDailyLimit` 已实现以下日额度调整：

| 信号 | enforce 时的日额度 | 当前恢复依据 |
| --- | --- | --- |
| 7 日接受数 > 30 且接受/已处理 > 90% | 接受 3 | 查询窗口中的比例/数量不再命中 |
| 最近 7 天拉黑记录内存在 24 小时被 3 人拉黑的窗口 | 举手 3 | 滑动记录不再命中 |
| 不同举报人的 pending 用户举报形成 24 小时内 3 人窗口 | 发布 2 | 举报被处理等使条件不再成立；需求举报不算这项 |
| 举手接受率 < 5%，已处理样本 ≥ 20 | 举手 5 | 当前接受率/样本不再命中 |

`QUOTA_P4_MODE` 默认 `shadow`：日额度保持基础值加赚回，仅在使用量达到候选惩罚上限时，记录限频的 `quota_penalty_shadow` 事件；UI 不显示已执行降额。显式 `enforce` 才使用惩罚日额度。上线配置需单独确认，代码默认值不证明线上实际取值。

`isHarvestingNeed` 另检查同一需求独立举手人数 > 30 且 accepted/completed 比例 > 80%，命中后拒绝新举手；该检查不受 `QUOTA_P4_MODE` 控制。与单需求接受数 10 的规则并存，目前正常受限写入很难达到这一阈值。没有自动创建「人工审核队列」或人工解除记录；管理员暂停账号是另一个治理操作。

阈值是产品初始参数，不是对正常用户接受率的实证结论。应观察真实分布后决定调整或开启 enforce。

## 11. 用户侧呈现与实现入口

- 「我的 → 额度」展示今日剩余和存量，收到/发起连接管理在独立 `/me/connections`。
- 发布剩余 ≤ 3 时提示；举手表单常驻等待回应数、当日剩余和交换预告；未处理收到举手 ≥ 5 时显示入口。
- 关闭需求可释放开放存量，不能返还已消耗的发布日额度。填好名片仍需注册满 72 小时才转常规档。
- `checkQuota(user, key, t, target?, now?)` 返回 `{ ok: true, remaining }` 或 `{ ok: false, reason, message }`，没有 `hint` 字段。`QuotaKey` 不含编辑与续期。
- `getQuotaSummary` 供 UI；`effectiveDailyLimit` 计算赚回和惩罚；服务在写路径调用它们。

入口：[`lib/quota.ts`](../lib/quota.ts)、[`lib/connections-service.ts`](../lib/connections-service.ts)、[`lib/safety-service.ts`](../lib/safety-service.ts)、[`components/quota-panel.tsx`](../components/quota-panel.tsx)。回归见 `tests/quota.test.ts`、`tests/connections.test.ts`、`tests/renewal-lock.test.ts`、`tests/safety.test.ts`。

## 12. 原设计未落地或仍需评估的项目

以下保留为差距，不是当前承诺；本轮只更新文档，没有补写代码：

- 编辑需求/名片 1 次/5 秒，以及所有用户写操作 30 次/分钟的统一兜底。
- 续期日额度 5/20、编辑名片日额度 30/50。
- 接受动作对双方 accepted 存量的对称检查、对举手方提供联系方式日揭示数的检查。
- 惩罚自动转人工队列，以及单需求异常检查的 shadow/enforce 一致性。
- 使用不可变事件或揭示账本统一重发、撤回、删除后的历史额度口径。
- 独立的举手/连接列表 API。当前 Agent 读取通知辅助判断，不能当作完整连接状态接口。

变更这些规则前同步 PRD、API 参考和相关测试；数值调整基于实际使用分布，不能把本文的原设计愿望当作已有防护。
