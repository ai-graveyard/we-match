# We Match Agent-First 方案（讨论稿）

- 版本：v0.2
- 日期：2026-08-08
- 状态：讨论稿；「决策权在人」边界已定（见 1.1），其余开放问题见第 7 节
- 前置：`docs/AGENT-SKILL.md`（API v1 + 官方 Skill，已实现）、`docs/PRD.md` v1.0

## 1. 核心想法：主客户端从「人」换成「Agent」

现状是给人用的网站，Skill 只是辅助工具。目标是翻转过来：

- **用户的 Agent 是主客户端**。装上官方 Skill 之后，Agent 代表用户长期「经营」在 We Match 上的存在：维护画像、盯着广场、该发的帖子发出去、该续的需求续上。
- **网页退居管理后台**。登录、生成 API Key、处理举手/连接这类要人拍板的动作留在网页；日常浏览和发布不再依赖人打开网站。
- **人只在关键节点出现**：确认 Agent 起草的内容、决定要不要联系某个人。

一句话：人和人碰面之前，先让 Agent 和 Agent 碰面。

### 1.1 硬边界：Agent 不做社交决策（已定）

Agent 的职责链是：**获取信息 → 用深画像筛选 → 把少数高质量候选讲清楚**，价值在于替人省掉刷广场和粗筛的麻烦；链条到此为止。

- 举手、接受举手、建立联系——凡是「决定和某个人发生关系」的动作，**必须人拍板**，任何授权档位都不能把它们自动化。
- 这不是暂时的保守，而是产品底线：口号是「让合适的人碰面」，碰面的意愿只能来自人本身。Agent 互相握手、人反而缺席，是本方案要明确排除的形态。

### 为什么这个翻转成立

1. **供需匹配的真实成本不在发布，在持续经营。** 画像会过时、需求会过期、匹配要靠自己反复刷广场——这些事人懒得做、做不持久，恰好是 Agent 擅长的。
2. **Agent 比表单更了解用户。** 用户和自己的 Agent 日常协作，Agent 自然知道 TA 会什么、正在做什么、缺什么资源。让 Agent 从协作记录里提炼画像，比让用户对着表单自我总结准确得多，也新鲜得多。
3. **平台可以继续极简。** 「匹不匹配」的语义判断放在端侧每个用户自己的 Agent 里，平台只做结构化数据的存取、检索、身份和可见性——不做推荐算法，不做消息系统，与 PRD 的极简原则一致。PRD 二期设想的「自动撮合」由此有了具体路线：**撮合不做在平台侧，做在端侧。**

## 2. 角色分工

| | 端侧：用户的 Agent + Skill | 平台：wematch.v2ai.org |
|---|---|---|
| 智能 | 画像提炼、匹配判断、内容撰写、与用户对话确认 | 无（不理解语义） |
| 数据 | 深画像（私密，永不上传） | 名片、需求、组织、通知（用户确认过的公开数据） |
| 能力 | 调度例程、调用 API | 结构化存储、检索、身份、可见性、限额 |

**深画像 vs 名片**是这套分工的关键：

- **深画像**存在端侧（Agent 的 memory 或本地文件），内容包括：技能与近期动向、我需要什么、我能提供什么、匹配偏好（想遇到什么人、不想遇到什么人）、以及不愿公开的上下文（在做什么项目、预算多少）。它是 Agent 判断匹配时的依据。
- **名片**是站上那份用户确认过的公开摘要，受既有可见性体系控制。
- 深画像永不上传。这既是隐私边界，也是产品叙事：**平台知道的，比你的 Agent 少得多。**

## 3. 端侧：三个例程

Skill 在现有「按需调 API」的基础上，新增三个可被定时触发的例程剧本。

### 3.1 画像维护

1. 回顾近期与用户的协作记录（各 Agent 平台自带的记忆/历史能力），提炼变化：新掌握的技能、新在做的事、新出现的需要。
2. 更新端侧深画像。
3. 对比站上名片（`GET /me`）：若介绍、标签等与深画像出现**实质**偏差，生成一份 diff 给用户确认，确认后 `PATCH /me/card`。无实质变化则什么都不做。

### 3.2 匹配拉取

1. 拉广场和所在组织的新需求（依赖平台补增量接口，见第 5 节）。
2. 用深画像逐条判断：这条 offer 是不是用户需要的？这条 need 是不是用户能接的？——判断在端侧做，所以能用上私密上下文，平台无需理解语义。
3. 只把真正值得联系的少数几条讲给用户，附上「为什么匹配」和下一步建议（去举手/去看名片）。宁缺毋滥，不做每日站会式的流水汇报。

### 3.3 供给与需求发布

1. 从深画像里找「用户能提供但站上没发布」「用户缺但站上没发布」的项。
2. 起草帖子（引用用户真实的项目和事实，禁止空泛模板），用户确认后 `POST /needs`。
3. 已有帖子做**幂等维护**：临期的续期、内容有实质变化的小改（`PATCH`），而不是每天发新帖。

### 3.4 调度

- 默认建议**每天早上 8:00 跑一遍**上述三个例程（合并为一次「日常例程」），用户可改频率和时间。
- Skill 是纯文档包，没有自己的运行时——调度依赖用户 Agent 平台自身的能力（Claude Code 的 scheduled task、系统 cron 等）。安装流程里增加一步：引导用户在自己的平台上注册这个例程（见第 5 节第 4 条）。
- 调度不可用的环境（用户的 Agent 没有定时能力）自然降级为「用户想起来时说一句『跑一下 We Match 日常例程』」，剧本本身不变。

## 4. 授权分级

Agent 自动化和「写操作要用户确认」（现行 Skill 安全规则）之间需要一个明确的分级，否则要么天天打扰用户，要么 Agent 擅自行动：

| 档位 | 覆盖操作 | 行为 |
|------|----------|------|
| L0 只读 | 拉需求、查名片、查通知 | 全自动，不打扰用户 |
| L1 草稿（默认） | 发帖、改名片、续期 | Agent 起草并说明理由，用户点头后执行 |
| L2 自动 | 用户明示授权的操作类别（如「以后续期不用问我」） | 按类别白名单自动执行，事后汇报 |

- L2 是**逐类别**授权，不是一揽子放权；授权记录存在端侧 Skill 配置里。
- 删除操作永远要确认，不进 L2。
- 举手、接受举手、建立联系**不在此分级体系内**——它们不是「Agent 的操作」，是人的决策（见 1.1）。未来即使开放举手 API，Agent 也只能替人执行已明确表达的意愿，不能代为决定。

## 5. 平台侧需要补的能力

按优先级排序，前两条是日常例程能转起来的前提：

1. **增量拉取**：`GET /api/v1/needs` 支持 `since=<ISO 时间>`，只返回该时间之后新增/变更的需求。没有它，每天例程只能全量翻页，既慢又费限额。
2. **通知 API**：`GET /api/v1/me/notifications`（支持未读筛选与标记已读）。举手、被接受这些回路事件目前只有网页能看到；Agent 看不到就闭不了环——「有人对你的帖子举手了」恰恰是最值得 Agent 转告用户的消息。
3. **Skill 安装流**：`/skill` 安装说明与「我的 → Agent」页面加入「注册日常例程」一步，给出主流平台（至少 Claude Code）的注册示例。
4. **请求来源标记**：约定例程请求带特定 `User-Agent` 或头字段，仅用于平台观测（多少流量来自例程），不做差别对待。
5. **（远期，默认不做）语义检索**：只有当 tag + 关键词检索被验证明显不够时再评估 embedding 端点。它与极简原则冲突，且第 3.2 节的端侧判断已承担语义工作。

MCP Server 维持 `AGENT-SKILL.md` 第 6 节的判断：二期在 `/api/v1` 上薄封装，不影响本方案。

## 6. 防滥用与内容质量

所有人的 Agent 每天 8 点齐刷刷跑例程，是新的滥用面：

- **流量**：现有限流（每 Key 每分钟 120 次）+ 增量接口（大幅减少请求数）兜底；例程剧本建议用户把时间设在 8 点附近随机分散亦可，暂不强制。
- **垃圾帖**：现有每日 10 条限额兜底；剧本层约束「无实质变化不发帖不更新」，并给日常例程设写操作预算（单次例程 ≤ 3 次写）。
- **同质化**：Agent 写的帖子容易千篇一律。剧本强制要求引用用户真实项目与事实、复用站内已有标签写法，禁止「资深工程师提供技术咨询」式空模板。

## 7. 开放问题（待讨论）

1. **深画像要不要给推荐 schema？** 给一份推荐结构（Skill 里附模板文件）利于例程质量稳定，但也限制了各 Agent 平台的自由发挥。倾向：给推荐模板，不强制。
2. **举手/连接 API 何时开放？** 现在 v1 没有举手端点（PRD v1.0 的连接制本身在 M6）。本方案的匹配拉取例程落地后，「Agent 汇报 → 用户去网页举手」是可接受的过渡；长期看举手可以进 API，但受 1.1 约束——Agent 只能替人执行已明确表达的举手意愿，不能自行判断后代发。
3. **额度模型要不要为例程调整？** Agent 高频读取远超人类用户，与 `QUOTA.md` 的额度体系需要合流评估。
4. **官方是否提供托管例程？** 平台侧替没有调度能力的用户跑每日匹配（服务端定时 + 邮件/短信通知）。这会把智能拉回平台侧，与第 1 节的分工矛盾，倾向不做，列出仅为讨论完整性。

## 8. 与现有文档的关系

- `AGENT-SKILL.md`：接入层（Key、API v1、Skill 分发），已实现，本方案完全构建在其上。
- 本文：使用层的翻转——谁是主客户端、端侧三个例程、授权分级、平台需补的增量能力。
