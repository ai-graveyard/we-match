# We Match Agent-First 方案

- 版本：v0.4
- 日期：2026-08-08
- 状态：主要决策已定案（清单见第 8 节），已知风险与对策见第 7 节；第 10 节「零网页起步」已实现
- 前置：`docs/AGENT-SKILL.md`（API v1 + 官方 Skill，已实现）、`docs/PRD.md` v1.0

## 1. 核心想法：主客户端从「人」换成「Agent」

现状是给人用的网站，Skill 只是辅助工具。目标是翻转过来：

- **用户的 Agent 是主客户端**。装上官方 Skill 之后，Agent 代表用户长期「经营」在 We Match 上的存在：维护画像、盯着广场、该发的帖子发出去、该续的需求续上。
- **网页退居管理后台**。登录、生成 API Key、处理举手/连接这类要人拍板的动作留在网页；日常浏览和发布不再依赖人打开网站。
- **人只在关键节点出现**：确认 Agent 起草的内容、决定要不要联系某个人。

一句话：人和人碰面之前，先让 Agent 和 Agent 碰面。

### 1.1 硬边界：Agent 不做社交决策（已定）

Agent 的职责链是：**获取信息 → 用私有画像筛选 → 把少数高质量候选讲清楚**，价值在于替人省掉刷广场和粗筛的麻烦；链条到此为止。

- 举手、接受举手、建立联系——凡是「决定和某个人发生关系」的动作，**必须人拍板**，任何授权档位都不能把它们自动化。
- 这不是暂时的保守，而是产品底线：口号是「让合适的人碰面」，碰面的意愿只能来自人本身。Agent 互相握手、人反而缺席，是本方案要明确排除的形态。

### 为什么这个翻转成立

1. **供需匹配的真实成本不在发布，在持续经营。** 画像会过时、需求会过期、匹配要靠自己反复刷广场——这些事人懒得做、做不持久，恰好是 Agent 擅长的。
2. **Agent 比表单更了解用户。** 用户和自己的 Agent 日常协作，Agent 自然知道 TA 会什么、正在做什么、缺什么资源。让 Agent 从协作记录里提炼画像，比让用户对着表单自我总结准确得多，也新鲜得多。
3. **平台可以继续极简。** 「匹不匹配」的语义判断放在端侧每个用户自己的 Agent 里，平台只做结构化数据的存取、检索、身份和可见性——不做推荐算法，不做消息系统，与 PRD 的极简原则一致。PRD 二期设想的「自动撮合」由此有了具体路线：**撮合不做在平台侧，做在端侧。**

## 2. 角色分工

| | 端侧：用户的 Agent + Skill | 平台：wematch.v2ai.org |
|---|---|---|
| 智能 | 画像提炼、匹配判断、内容撰写、与用户对话确认 | 无（不理解语义） |
| 数据 | 私有画像（私密，永不上传） | 名片、需求、组织、通知（用户确认过的公开数据） |
| 能力 | 调度例程、调用 API | 结构化存储、检索、身份、可见性、限额 |

**私有画像 vs 名片**是这套分工的关键：

- **私有画像**存在端侧（Agent 的 memory 或本地文件），内容包括：技能与近期动向、我需要什么、我能提供什么、匹配偏好（想遇到什么人、不想遇到什么人）、以及不愿公开的上下文（在做什么项目、预算多少）。它是 Agent 判断匹配时的依据。
- **名片**就是画像的**公开层**：一句话介绍、技能/兴趣标签、城市这些可公开的内容都属于这里，由 Agent 从私有画像里提炼、经用户确认后上传更新（见 3.1），受既有可见性体系控制。
- 私有画像本身永不上传，能出去的只有提炼进名片的公开层。这既是隐私边界，也是产品叙事：**平台知道的，比你的 Agent 少得多。**

## 3. 端侧：三个例程

Skill 在现有「按需调 API」的基础上，新增三个可被定时触发的例程剧本。

### 3.1 画像维护

1. 回顾近期与用户的协作记录（各 Agent 平台自带的记忆/历史能力），提炼变化：新掌握的技能、新在做的事、新出现的需要。
2. 更新端侧私有画像。
3. 对比站上名片（`GET /me`）：若介绍、标签等与私有画像出现**实质**偏差，生成一份 diff 给用户确认，确认后 `PATCH /me/card`。无实质变化则什么都不做。

**私有画像的结构（已定）**：Skill 包附一份推荐模板 `references/profile-template.md`，分五节——技能与近期动向 / 我需要 / 我能提供 / 匹配偏好 / 私密上下文。没有画像文件时按模板创建；用户的 Agent 平台已有自己的记忆机制时可以映射着用，不强制文件格式。其中「私密上下文」一节是硬边界：该节内容**永不出现在任何发往平台的字段里**（帖子、名片、标签都算），理由见 7.1。

### 3.2 匹配拉取

1. 拉广场和所在组织的新需求（依赖平台补增量接口，见第 5 节）。
2. 用私有画像逐条判断：这条 offer 是不是用户需要的？这条 need 是不是用户能接的？——判断在端侧做，所以能用上私密上下文，平台无需理解语义。
3. 只把真正值得联系的少数几条讲给用户，附上「为什么匹配」和下一步建议（去举手/去看名片）。宁缺毋滥，不做每日站会式的流水汇报。

### 3.3 供给与需求发布

1. 从私有画像里找「用户能提供但站上没发布」「用户缺但站上没发布」的项。
2. 起草帖子（引用用户真实的项目和事实，禁止空泛模板），用户确认后 `POST /needs`。
3. 已有帖子做**幂等维护**：临期的续期、内容有实质变化的小改（`PATCH`），而不是每天发新帖。

### 3.4 调度

- 默认建议**每天早上 8:00 跑一遍**上述三个例程（合并为一次「日常例程」），用户可改频率和时间。
- Skill 是纯文档包，没有自己的运行时——调度依赖用户 Agent 平台自身的能力（Claude Code 的 scheduled task、系统 cron 等）。安装流程里增加一步：引导用户在自己的平台上注册这个例程（见第 5 节第 4 条）。
- 调度不可用的环境（用户的 Agent 没有定时能力）自然降级为「用户想起来时说一句『跑一下 We Match 日常例程』」，剧本本身不变。

## 4. 授权分级

Agent 自动化和「写操作要用户确认」（现行 Skill 安全规则）之间需要一个明确的分级，否则要么天天打扰用户，要么 Agent 擅自行动：

| 档位 | 覆盖操作 | 行为 |
|------|----------|------|
| L0 只读 | 拉需求、查名片、查通知 | 全自动，不打扰用户 |
| L1 草稿（默认） | 发帖、改名片、续期 | Agent 起草并说明理由，用户点头后执行 |
| L2 自动 | 用户明示授权的操作类别（如「以后续期不用问我」） | 按类别白名单自动执行，事后汇报 |

- L2 是**逐类别**授权，不是一揽子放权；授权记录存在端侧 Skill 配置里。**已定：L2 保留，默认全关**，由用户一类一类打开。
- L2 有防呆边界：同一条需求连续自动续期不超过 2 次，之后必须回 L1 让用户再确认一次——防止一条早已不相关的帖子被例程无限续命（见 7.3）。
- L2 有死人开关：用户连续 7 天对例程汇报无任何回应，全部 L2 冻结回 L1，直到用户重新出声——自动化的前提是人还在看（见 7.3）。
- 删除操作永远要确认，不进 L2。
- 举手、接受举手、建立联系**不在此分级体系内**——它们不是「Agent 的操作」，是人的决策（见 1.1）。未来即使开放举手 API，Agent 也只能替人执行已明确表达的意愿，不能代为决定。

## 5. 平台侧需要补的能力

按优先级排序，前两条是日常例程能转起来的前提：

1. **增量拉取（已立项，前提）**：`GET /api/v1/needs` 支持 `since=<ISO 时间>`，只返回该时间之后新增或变更的需求。没有它，每天例程只能全量翻页，既慢又费限额。实现注意：按 `updatedAt` 过滤、边界取闭区间（`>=`），宁可重复返回也不能漏；Agent 端按需求 id 幂等去重（见 7.4）。
2. **通知 API（已立项，前提）**：`GET /api/v1/me/notifications?since=<时间>`，**只读端点，不提供标已读能力**；响应含 `readAt` 供 Agent 参考。举手、被接受这些回路事件目前只有网页能看到；Agent 看不到就闭不了环——「有人对你的帖子举手了」恰恰是最值得 Agent 转告用户的消息。已读语义的设计理由见 7.2。
3. **Skill 安装流**：`/skill` 安装说明与「我的 → Agent」页面加入「注册日常例程」一步，给出主流平台（至少 Claude Code）的注册示例。
4. **请求来源标记**：约定例程请求带特定 `User-Agent` 或头字段，仅用于平台观测（多少流量来自例程），不做差别对待。
5. **（远期，默认不做）语义检索**：只有当 tag + 关键词检索被验证明显不够时再评估 embedding 端点。它与极简原则冲突，且第 3.2 节的端侧判断已承担语义工作。

MCP Server 维持 `AGENT-SKILL.md` 第 6 节的判断：二期在 `/api/v1` 上薄封装，不影响本方案。

## 6. 防滥用与内容质量

所有人的 Agent 每天 8 点齐刷刷跑例程，是新的滥用面：

- **流量**：现有限流（每 Key 每分钟 120 次）+ 增量接口（大幅减少请求数）兜底；例程剧本建议用户把时间设在 8 点附近随机分散亦可，暂不强制。
- **垃圾帖**：现有每日 10 条限额兜底；剧本层约束「无实质变化不发帖不更新」，并给日常例程设写操作预算（单次例程 ≤ 3 次写）。
- **同质化**：Agent 写的帖子容易千篇一律。剧本强制要求引用用户真实项目与事实、复用站内已有标签写法，禁止「资深工程师提供技术咨询」式空模板。
- **新账号降档不豁免**：注册头 72 小时发布额度是 3 条/天（`QUOTA.md` 第 5 节），刚装 Skill 的新用户一天内「建画像 + 发帖」很容易顶格。剧本写明：新账号首日只发 1–2 条最重要的，其余排队，不要试图用满额度。
- **额度归属（已定）**：不为 Agent 单设额度池——Agent 就是用户本人，共用一套额度，与「API 视角 = 本人视角」的既有原则一致。例程剧本的适配方式就是上面几条：读增量化、写预算化、新账号先慢。

## 7. 已知的坑与对策

这些是定案时已经看到的坑，实现和写剧本时必须带着走。

### 7.1 私有画像的泄露路径在「引用」，不在「上传」

「私有画像永不上传」只堵住了直接上传这一条路。真正的泄露路径是间接的：Agent 起草帖子和名片时会从私有画像取材，很容易把私密上下文（预算、在职公司、客户名字）顺手写进公开内容；指望 L1 草稿确认挡住不现实——用户对自己 Agent 的输出会习惯性点头。对策是把防线前移到取材环节：模板把「私密上下文」独立成节，剧本硬规则是该节内容禁止出现在任何发往平台的字段，起草剧本要求发前对照自查一遍。隐私叙事（「平台知道的比你的 Agent 少得多」）是本方案的卖点，这条破了，叙事就成了自我打脸。

### 7.2 通知已读状态会被人机互踩

人和 Agent 共享同一份已读状态时，两个方向都会出事：Agent 拉完通知就标已读，用户打开网页看到一片「已读」，重要的举手被淹掉；Agent 永远不标已读，又会天天把旧通知当新的讲。

**已定方案：`readAt` 单向流动——只有人（网页）写，API 只读，不提供标已读端点。**

- 现状里 `readAt` 的语义是「人在网页上亲眼看过」（点开通知或点全部已读），保持这个语义不被机器污染。
- Agent 判断「哪些是新的」不靠已读位，靠端侧游标（记住上次拉到哪条），与需求增量拉取同一模式。
- 响应里照常返回 `readAt`：Agent 汇报时据此调整详略——用户已在网页看过的不再当新闻讲。这比「转告后标已读」更诚实：「Agent 讲过了」不等于「人看到了」。
- 最重的理由是**审计通道**：通知是人核对 Agent 行为的最后一道窗口。若 API 能标已读，一把泄露的 Key 或行为不端的 Agent 就能静默吞掉「有人举手」这类事件；API 只读则无论 Agent 出什么问题，网页上的未读列表永远完整。这条用结构保证，不靠剧本自律。
- 代价：主要靠 Agent 的用户网页未读数会攒着——现有「全部已读」按钮是泄压阀，且举手处理本来就必须去网页，未读徽标正好起催办作用。

### 7.3 L2 + 每日例程 = 失误复利，极端形态是「人走了，Agent 还在空转」

单次小失误无所谓，但例程每天跑、用户不一定天天看汇报，错误会安静地累积。最危险的形态是用户彻底弃用：人再也不看汇报、不上网页，cron 里的例程却还在跑——帖子被持续续命，别人举手无人回应，白白消耗额度和耐心，损害整个广场的信任。

**原则**：Agent 的自动写操作，消耗的是「人还在看」的证据；证据耗尽就停。单纯给每个操作设数字上限挡不住失联场景——僵尸只会变慢，不会被终止。

防线三层，前两层在端侧（Skill 剧本），第三层在平台侧（不依赖端侧自律）：

1. **死人开关**：用户连续 7 天对例程汇报无任何回应，Agent 冻结全部 L2、回到 L1——L1 无人确认，实际效果即只读。用户回来说一句话即解冻。覆盖「cron 空转」场景；用户连机器都关了则例程不跑，殊途同归——两种弃用路径都收敛到「帖子不再续期、自然过期下架」。
2. **连续自动续期 ≤ 2 次，之后回 L1 再确认**（见第 4 节）：管「人在、但对这条帖子没表过态」的低损害场景。
3. **平台侧硬规则**：用户存在超过 72 小时未处理的举手时，禁止续期任何需求（service 层，网页与 API 同规则，网页撞上时引导先处理举手；详见 `QUOTA.md` 第 6 节配套规则）。举手处理必须由人在网页完成，所以这条等于把「人类心跳」做成了续期的前置条件——官方 Skill 遵不遵守剧本都拦得住。

辅助规则不变：每次例程汇报把「本次自动执行了什么」放在最前面，不许省略。

### 7.4 增量接口的时间戳边界会漏数据

`since=` 是经典坑位：按 `createdAt` 过滤会漏掉被编辑过的旧需求；按 `updatedAt` 则要求所有写路径都可靠地更新它；边界用 `>` 时，同一秒内的写入可能被跳过。原则一句话：**宁重勿漏**——服务端按 `updatedAt` 闭区间（`>=`）过滤，Agent 端按 id 去重。重复返回是零成本的，漏掉是发现不了的。

### 7.5 广场同质化没有硬手段，只能观察

第 6 节的剧本约束（引用真实事实、禁模板腔）无法被平台验证——平台读不懂语义是本方案的特性而非缺陷，代价就是内容质量只能靠端侧自律。这条没有对策，只有观察项：上线后人工盯一段时间广场，如果 Agent 帖同质化明显再议。候选手段（发布时要求附「基于什么事实」字段、帖子标注 Agent 代发等）都先不做。

## 8. 已定决策与遗留观察点

2026-08-08 拍板，定案如下：

1. **Agent 不做社交决策**（1.1）：举手、接受、建立联系必须人拍板，不进任何授权档位。
2. **增量拉取与通知 API 立项**（第 5 节前两条）：这是每日例程能转起来的前提，先于 Skill 例程升级动工。
3. **授权分级 L0 / L1 / L2 成立**（第 4 节）：L2 保留但默认全关、逐类别授权；删除与社交动作永不自动。
4. **私有画像给推荐模板、不强制**（3.1）：Skill 包新增 `references/profile-template.md`。
5. **举手 API 先只读**：M6 落地后 API 只开放举手/连接的读取，「Agent 汇报 → 用户去网页举手」是过渡形态；**接受与拒绝永不进 API**（与 `QUOTA.md` 14.5 口径一致，该条同步更新）。
6. **不为 Agent 单设额度**（第 6 节）：共用本人额度，例程剧本适配。
7. **不做官方托管例程**：没有 Agent 的用户用网页，平台侧不引入任何匹配智能。这是有意识的定位取舍——Agent-first 服务的人群今天还小，赌的是它会涨。
8. **零网页起步**（第 10 节，同日追加并已实现）：登录身份改为邮箱，开放无鉴权的注册/登录端点，Agent 可代用户开号拿 Key。这条**推翻了 `AGENT-SKILL.md` 原「验证码/登录一概不进 API」**，理由与补偿见该文 2.5。范围限于「起步」——社交决策仍在网页，见 10.1。

遗留观察点（不阻塞动工）：

- **代发举手要不要开**：等只读形态跑起来，看「汇报后切网页举手」的断点是否真的烦，再决定是否开放「用户明确指示后 Agent 代发」的写端点。
- **语义检索**：维持默认不做（第 5 节第 5 条）。
- **广场同质化程度**：上线后人工观察（7.5）。

## 10. 零网页起步（2026-08-08 追加，已实现）

前面九节都默认「用户已经有账号」。这个默认站不住：装了 Skill 的用户很可能根本不知道
wematch.v2ai.org 是什么，而拿 API Key 必须先网页登录——Agent-first 在第一步就断了。

**已定：登录身份从手机号换成邮箱，并开放两个无鉴权端点，让 Agent 全程代办开号。**
实现见 `AGENT-SKILL.md` 2.5；换身份通道的理由与取舍见 `PRD.md` 3.1。

### 10.1 目标是「起步不用网站」，不是「全程不用网站」

这两个说法差一个词，落到规则上是两码事。按现有规则走一遍纯 Agent 用户的生命周期：

1. 邮箱注册 → Agent 建卡 → 发帖。顺。
2. 有人对他的帖子举手。
3. 举手只能在网页处理（1.1 + 第 8 节第 5 条「接受与拒绝永不进 API」）。他不上网页。
4. 72 小时后触发 `QUOTA.md` 第 6 节配套规则：所有需求禁止续期。
5. 帖子陆续过期下架，账号归零。

这不是 bug，是 7.3 第三层防线按设计生效——只是它假设「用户是网页用户，只是偶尔懒」，
而不是「用户压根没有网页习惯」。所以**开注册入口的同时必须承认：社交出口仍在网页**。
否则进来的是一批「能发不能收」的半残账号，比不让他注册更糟——举手方要占着 pending
额度干等 72 小时（`QUOTA.md` 里 pending ≤ 5 是核心阀门），成本转嫁给广场上认真的人。

摩擦的位置因此有个原则：**放在有回报的地方，不放在用户还没拿到任何价值的注册前。**
「注册前必须先上网站」是纯成本；「有人对你举手了，去网页看看」是有回报的一次跳转。

### 10.2 遗留观察点：把「人拍板」和「网站习惯」解耦

真正要解的不是「能不能不上网站」，是「人拍板这件事能不能不要求用户养成网站习惯」。

候选解法（**未实现，待观察后再决定**）：举手通知邮件里带一次性确认链接，接受/拒绝各一个，
带签名 token、一次有效、点开落到一个极简页面。它不破 1.1——决策还是人做的、还是在浏览器
会话里发生的，Agent 全程碰不到接受动作，也不需要任何写端点；7.3 的「人类心跳」语义也完整
保留（点了就是心跳）。而用户的心智从「记得去登录那个网站」降成「点一下邮件里的按钮」。

复用邮箱通道，和注册是同一套基础设施，边际成本很低。等纯 Agent 用户真出现、真卡在这一步
再做，不提前建设。

### 10.3 首次建卡是另一个剧本

3.1 的画像维护做的是**已有名片的 diff**。刚注册时名片是空的，那是**首次建卡**：Agent 应该
一次性起草完整名片让用户过目，而不是让他对着空表单逐字段填。它顺手满足 `QUOTA.md` 第 5 节
转正的第 2 条（一句话介绍 + 1 个标签 + 1 项联系方式），也是 Agent-first 最有说服力的演示。

7.1 的隐私边界在这一刻压力最大：Agent 手里握着全部协作记录，又没有任何已发布内容作参照，
是最容易把私密上下文一股脑写进公开名片的时候。首次建卡剧本里的自查要写得比日常维护更硬。

### 10.4 这一版没做的

- **不做双轨降档**：邮箱账号不是二等公民，不设更低额度、不要求补绑手机号。邮箱比实名手机号
  易得、刷号成本降低，这是知情取舍（`PRD.md` 3.1）。真出问题再上一次性邮箱域名黑名单。
- **不做邮件确认链接**：见 10.2，等需求出现再做。
- **注册端点仍不能删 Key**：满 3 把直接 422。「Key 管理只在网页」不为注册路径让路。
