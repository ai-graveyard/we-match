# We Match 下一阶段：验证真实需求能否得到回应

本轮优先完善首次发布、候选发现、通知触达和结果统计。核心判断是：用户带着具体问题进来，能否更快找到愿意回应、条件合适的人。

## 已实现的产品改动

- 广场尊重城市隐藏设置，详情页尊重简介隐藏设置；公开查询不下发隐藏城市。
- 广场类型明确为「有人需要 / 有人提供」；每页 20 条，展示真实总数，支持前后翻页。筛选、范围和排序变化回到第一页。
- 搜索无结果可清除筛选或发布需求，空广场也有发布入口。
- 发布表单提供供需写作提纲，引导说明目标、合作方式、时间、地点、经验或参考链接。模板只在描述为空时插入，用户主动选择填写公开信息。
- 首次发布缺可用联系方式时，可以在当前页补昵称和一项空的联系方式。服务端校验后与需求原子保存，默认连接后交换；不覆盖已有、隐藏或被其他标签页修改的联系方式。
- 草稿按用户和需求保存在当前标签页的 sessionStorage；回到表单后由用户选择恢复，不覆盖当前输入。草稿不保存联系方式原值。发布或保存成功只清除对应提交标识的草稿，旧成功链接不会删除新草稿。关闭标签页或浏览器清理数据后不保证保留。
- 自己的开放需求详情展示最多三位不同发布者的候选。反向类型、同范围、未过期和权限是硬条件；共同标签只用于排序，页面明确提示用户核对合作条件。没有候选时提示分享需求和浏览同范围供需。
- 匹配通知直达需求的候选区，保留组织范围；Agent API 继续返回原有的逐条需求候选，不执行社交决策。
- 举手、接受与拒绝结果在响应后触发邮件。仅使用固定 SITE_ORIGIN 和登录邮箱，邮件不含联系方式和举手留言；检查收件人状态、偏好及组织成员关系。投递失败保留站内通知并记录不含邮箱的错误；当前没有持久邮件队列或自动重试。
- 「我的 → 设置」可关闭连接邮件。发送需要 Resend 和有效 SITE_ORIGIN；本地 log 通道不会发送连接邮件。
- 后台增加同一批需求的七天结果，按需求去重统计收到举手、接受及双方确认完成。最近三十个发布日中，只有已观察满七天且有发布事件的需求进入分母；每个阶段限定在发布后的七天内。无首个举手数据时显示空值，不填零。

## 第一轮运营实验

建议从能触达的 AI 独立开发者圈子开始，优先验证界面评审、架构咨询和短期协作。该选择是运营实验范围，不限制平台其他用户。

1. 找到一位愿意协作的社群负责人，邀请 50–100 位目标用户，其中约 20 位确认愿意响应需求的供给方先入场。
2. 收集至少 30 条用户当前真实存在的需求。每条说清问题、预期结果、合作方式和时间；不把演示帖子计入结果。
3. 初期人工帮助补充候选。每次记录是否人工介入，分别判断服务价值和产品自动完成能力。
4. 在 48 小时和第七天核对：有没有有效回应、有没有开始沟通、条件哪里不合适、最后发生了什么。
5. 记录无结果的原因：没有供给、条件不清、提醒没有触达、对方无暇处理、缺乏信任、条件谈不拢。按照原因决定下一轮改动。

试验门槛可先设为一半需求在 48 小时内得到有效回应、三成进入实质沟通，并出现用户主动再次使用。这些是初始决策门槛，不是行业基准；样本小时同时报告分子和分母。

「有效回应」指针对需求说明能力、条件或可执行下一步的回应，不能用任意举手替代。后台的收到举手只是行为指标；双方完成也只是当事人确认，不证明交易成交。语义质量、开始沟通和失败原因暂通过人工回访记录，不从现有事件计数推断。

## 后续观察项

- 候选提醒摘要、未处理举手的有限提醒和持久邮件重试：观察触达率及未处理原因后再确定频率。
- 独立作品链接、相关项目经历：先看模板中的链接是否足以帮助决策，再决定是否扩展名片字段。
- 标签同义词、语义召回：先收集真实漏配例子，继续保持私有画像在端侧。
- 分范围、供需方向和获客来源统计结果；观察有第二次需求的用户是否再次使用。
- 达到结果门槛后再测试组织管理增值服务或人工匹配服务的付费意愿。

上线验证还需使用真实收件箱检查 Resend 投递、跳转回原需求和邮件关闭设置；开发测试和模拟 MailProvider 不能证明真实邮件送达。部署前备份数据库，新迁移仅增加 users.connection_email_enabled，不改变旧字段或重建表。
